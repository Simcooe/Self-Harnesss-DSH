# ShopSimulator 场景难点分析

## 一句话理解

ShopSimulator 不是“帮用户搜一个差不多的商品”，而是让 Agent 在用户需求没有一次说全、用户画像可能误导、商品高度相似、规格容易选错的情况下，经过二三十步操作，最终买中唯一正确的 SKU。

可以把它想象成：Agent 带着用户走进一个有大量相似商品的淘宝迷宫，一边询问用户，一边搜索和比较，最后还必须确认自己实际选中的商品规格确实正确。

## 一个完整的购物过程

用户一开始只说：

> 我想买一双羽毛球鞋。

但真正需要满足的条件可能包括：

- 预算约 500 元；
- 白蓝配色；
- 40 码；
- 减震、耐磨；
- 偏好 YONEX；
- 希望是正品。

Agent 需要完成类似下面的过程：

```text
询问需求
→ 搜索商品
→ 浏览候选
→ 查看详情
→ 发现缺少信息并继续询问
→ 比较相似商品
→ 选择颜色和尺码
→ 确认当前价格
→ 获得用户确认
→ 购买
```

真正困难的地方，是这条链路中的每一步都依赖前面的判断。

## 六个核心难点

### 1. 用户不会一次把需求说全

Agent 可能知道“要买羽毛球鞋”，但不知道预算、颜色或尺码。

此时存在三个风险：

- 不询问就开始搜索，后面很可能买错；
- 把所有属性都问一遍，浪费操作步数；
- 问了不合适的问题，用户没有提供真正关键的信息。

因此，Agent 必须判断：

> 现在缺少什么信息？下一句最值得问什么？

这已经不是简单的指令执行，而是一个持续的需求澄清过程。

### 2. 用户画像既有用，又可能把 Agent 带偏

画像可能显示：

- 用户经常购买 YONEX；
- 用户通常穿 40 码；
- 用户最近搜索过减震羽毛球鞋。

这些信息可以帮助 Agent 缩小搜索范围，但不一定是本次购物的硬性要求。

例如，画像显示用户偏好 YONEX，但用户这次明确说“不要 YONEX”。此时当前需求必须覆盖历史偏好。

Agent 必须区分：

- 用户这次明确提出的要求；
- 用户长期稳定的偏好；
- 仅仅是从历史行为推测出的倾向；
- 已经被用户后来修改或拒绝的信息。

如果完全忽略画像，搜索空间会变大；如果把画像全部当成硬约束，又可能错过真正合适的商品。

### 3. 搜索结果高度相似，搜索本身不是终点

ShopSimulator 的同一细分类目中有大量高度相似的商品。搜索结果可能出现：

- A：白蓝色、减震，但没有 40 码；
- B：40 码、减震，但不是正品；
- C：白蓝色、40 码，但超过预算；
- D：条件都满足，但关键信息只在详情页中出现。

因此，Agent 不能只看搜索结果标题，而要在候选之间进行细粒度区分。

更困难的是，Agent 需要记住：

- 哪个商品满足哪些要求；
- 哪个商品还缺少哪些证据；
- 哪个商品已经被淘汰；
- 哪个候选其实比当前商品更匹配。

如果这些信息只存在于不断增长的对话上下文里，Agent 很容易重复搜索，或者放弃之前已经找到的高匹配候选。

### 4. 找对商品，不等于选对 SKU

即使商品本身正确，具体规格仍然可能错误：

- 选成 37 码而不是 40 码；
- 选错颜色；
- 切换规格后价格超过预算；
- Agent 以为点击成功，但页面实际上没有接受这个选择；
- 规格选择成功后没有重新检查当前价格。

论文 Figure 1 展示了一个典型问题：Agent 想选择白蓝色和 40 码，但环境返回当前尺寸仍然是 37，Agent 却继续购买。

这说明 Agent 不能只记住“我刚才点击了 40”，而必须确认：

> 页面当前真实状态到底是什么？

### 5. 用户可能在过程中改变需求

购物不是一次性指令。用户可能在看到候选后说：

- “这个颜色不喜欢”；
- “预算最多 400 元”；
- “还是想要耐磨一点的”；
- “刚才那个商品不要买了”。

如果 Agent 仍然沿用旧需求或旧的购买确认，就会出现“用户已经拒绝，Agent 仍然购买”的错误。

因此，后续的新信息必须能够覆盖旧信息，之前的候选和确认也可能随之失效。

### 6. 长轨迹会放大前面的错误

单独看，搜索、点击、询问和购买都不复杂。困难在于它们要连续执行几十步。

例如：

```text
第 1 步：用户说想买羽毛球鞋
第 5 步：用户补充预算
第 10 步：Agent 找到一个候选
第 15 步：用户拒绝某个颜色
第 20 步：Agent 切换了规格
第 25 步：页面实际规格没有切换成功
第 26 步：Agent 仍然购买
```

前面一个没有记录清楚的小错误，可能一直被带到最后，最终导致整条轨迹失败。

这也是为什么“模型看起来大部分步骤都做对了”，完整成功率仍然很低。

## 评分为什么特别严格

ShopSimulator 不是“推荐一个大致合适的商品”就算成功。最终商品需要同时满足多个维度：

- 类别；
- 商品属性；
- 颜色、尺寸、容量等选项；
- 价格。

只要其中一个关键属性或规格不满足，即使类别和价格都正确，也可能无法获得完整成功。

所以它更像一场“全字段验收”，而不是普通的推荐任务。

## 难点的本质

ShopSimulator 最核心的问题，是下面三种状态必须在整个长轨迹中保持一致：

```text
用户现在想要什么
        ↕
已经找到哪些商品证据
        ↕
页面当前实际选中了什么
```

任何一个状态发生漂移，都会导致后续决策错误：

- 意图错了：搜索方向错；
- 证据丢了：重复搜索或放弃好候选；
- 页面状态错了：买错颜色、尺码或价格。

因此，ShopSimulator 的本质不是单纯的搜索问题，也不是单纯的记忆问题，而是一个持续几十步的“意图—证据—操作状态同步”问题。

这正是它适合作为长程购物 Harness 项目的根本原因。
